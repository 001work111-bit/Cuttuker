# Добавление нового формата адаптации: что пошло не так в 9:16 и как проверять

Дата фиксации: 2026-10-13. Относится к версии `v4_Sandbox_9x16_fix` (файлы `recompose-core.js`, `recompose-sandbox.js`, `CHANGES_9x16.md`).

## 1. Симптомы, которые видел пользователь
- В режимах «Один» и «Карта» кадр 9:16 обрезался справа и снизу.
- В «Карте» кадр выглядел как горизонтальный прямоугольник с белыми полями.
- В «Один» кадр был выше окна, и нижняя часть (сетка) не была видна.
- Методы адаптации из лаборатории (Recompose Studio) при этом выглядели правильно.

## 2. Что было на самом деле (корневые причины)

### 2.1. Масштаб сцены через выражение, которое не поддерживается у пользователя (главная причина обрезки)
- В `rcFragment` (`recompose-core.js`) сцена `.rc-stage` имела два объявления `transform`:
  - `transform:scale(k)`, где `k = previewW / fmt.w` (для 9:16 это 720/900 = 0.8);
  - `transform:scale(calc(100cqw / 900px))` — масштаб по ширине контейнера через контейнерные единицы.
- Старые Chromium/Electron не понимают `calc` внутри `scale()`. Тогда второе объявление отбрасывается, остаётся `scale(0.8)`.
- Для 16:9 это давало правильный результат только случайно: ширина кадра в предпросмотре равна 1280 = previewW, и 0.8 совпадало.
- Для 9:16 кадр 324 px ширины, а сцена масштабировалась на 0.8 (720 px). Выход: 396 px справа и 704 px снизу. Воспроизведено замером, совпадает со скриншотами пользователя.
- Почему это не было видно в тестах: тестовый браузер (Playwright Chromium) выражение понимает, поэтому замеры показывали корректный масштаб 0.36 и отсутствие обрезки.

### 2.2. Жёсткая привязка 1600×900 в слое адаптации
- Изначально `targetCss()` и правила `.sv-section` содержали 1600px/900px. Это было сделано под 16:9 и не зависело от формата.
- Импорт JSON в других форматах работал, а адаптация — нет, потому что слой адаптации считал кадр фиксированным.
- Исправлено: размеры берутся из `fmt` (`FW`/`FH`), вертикальные правила вынесены в `portraitCss` (побайтно из лаборатории) и подключаются только для кадров h > w.

### 2.3. Рамка карточки «Карта» и предпросмотр «Один»
- Высота рамки карточки считается по высоте сцены (`fitCard`). Если сцена неверно масштабирована (п. 2.1), рамка тоже неверная.
- Предпросмотр «Один» не вписывал портретный кадр в высоту окна. Исправлено скриптом `fitPortrait` (ширина контейнера ограничивается высотой окна, 9:16 помещается целиком).

### 2.4. Ошибки в процессе работы (что мешало)
- Сравнивались только вертикальные координаты блоков; горизонталь (ширина сетки) не проверялась.
- В замере вида «Один» захватывался исходный предпросмотр, а не результат (см. скриншот с «Real size 1280×657» в правой панели).
- Метод `editorial` в лаборатории — другой макет; нужный метод для проверки — `gemini.editorial` (в Sandbox — `gemini-editorial`). Сравнивались не те методы.
- Ограничение высоты внутри `rcFragment` вносилось без одобрения, его пришлось откатить.
- Отчёт `TEST_REPORT_9x16.md` в ранней версии был неполным и требовал исправления.

## 3. Что изменено в v4 (зафиксировано)
- `recompose-core.js` (`rcFragment`): удалено `transform:scale(calc(100cqw / Npx))`. Оставлено только `transform-origin:0 0`; масштаб задаёт скрипт.
- `recompose-sandbox.js` (блок в конце файла):
  - `fitStage(frame)`: масштаб сцены = `frame.clientWidth / 900` (ширина из `style.width` сцены). Не использует `calc` в `transform`.
  - `ResizeObserver` на каждом `.rc-frame` и `MutationObserver` на `document.body` (галерея создаётся позже, поэтому корни ищутся заново).
  - `fitPortrait()`: портретный кадр (h > w) в «Один» вписывается по высоте окна.

## 4. Проверено (замеры в тестовом браузере, 9:16, styleguideCustomerPortraits)
- «Один», окно 1568×823, 6 методов (smart, compact, split, fit, gemini-editorial, gemini-media-grid): кадр 324×576, выход контента 0 px справа и снизу.
- «Карта», те же методы: кадр 418×743, содержимое совпадает с кадром, выход 0, пустых полей справа и снизу 0.
- 16:9 «Карта»: размеры совпадают с исходной версией. У `compact` и `fit` выход 7–8 px по низу — было до правок, не изменено.
- Не проверено: версия Electron пользователя (вручную, по его скриншотам).

## 5. Чек-лист для новых форматов (4:3, 1:1 и далее)
1. **Не использовать `calc` внутри `transform`, `zoom` или другого свойства, которое может не поддерживаться.** Масштаб считать в JS по фактической ширине/высоте кадра.
2. **Размеры формата только из реестра `FORMATS`** (`w`, `h`). Никаких захардкоженных 1600/900 или 900/1600 в слое адаптации.
3. **Вертикальные (h > w) и горизонтальные правила разделять.** Новый формат с h > w — `portraitCss`-подобный блок из лаборатории, побайтно. Для 4:3 и 1:1 сначала найти эталон в лаборатории.
4. **Проверять в том же виде, что видит пользователь:** «Один» (Desktop) и «Карта», окно не меньше 1568×823. Замерять `frame`, `stage` и `overRight`/`overBottom` (контент относительно кадра), а не только y-координаты.
5. **Сравнивать с лабораторией по обеим осям** для тех же методов. Метод называть по ключу из реестра Sandbox (например, `gemini-editorial`).
6. **Проверять 16:9 на регрессию** теми же замерами: размеры кадра и выход за кадр должны совпасть с предыдущей версией.
7. **Не вносить ограничения размеров внутри шаблонов без одобрения.** Вписывание предпросмотра делается только в `recompose-sandbox.js`.
8. **Перед отдачей архива** проверить, что `CHANGES_*.md` описывает изменения, и что старые архивы помечены как неактуальные.
